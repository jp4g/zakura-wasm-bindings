# Private native account balance query

`initializeViews(...).call(generation, instance, 'account_balance', args)` uses the existing wallet owner and database. Arguments require an explicit canonical UUID `accountId` and `confirmations: { trusted, untrusted, allowZeroConfirmationShielding }`; the two counts are nonzero u32 values with trusted <= untrusted. The optional `signal` must be a native AbortSignal. There is no implicit policy or account selection.

The read-only result is `{ accountId, amounts }`. `amounts` is null when the native wallet summary is unavailable. An unknown valid account throws `ACCOUNT_NOT_FOUND`, even when summary data is unavailable. A present summary uses native zero buckets for empty pools. No missing native summary/account entry is replaced with fabricated zeros.

Amounts follow the planned WalletBalance amounts structure: account total, uneconomic, checked observedTotal; transparent regular/coinbase; Sapling; Ironwood; and nullable unsupportedLegacy `{ kind: 'legacyOrchard', balance }`. Every bucket contains total, spendable, locked, changePendingConfirmation, pendingSpendability, and uneconomic. Rust uses native getters and checked Zatoshis addition, emits decimal strings, and JavaScript converts only amount fields to bigint. Legacy Orchard is present when any native legacy bucket is nonzero. Locks remain included once in native totals; no reservations are subtracted again. Native purpose and confirmation classification remain authoritative.

The operation uses WalletRead::get_wallet_summary with ConfirmationsPolicy::new on the existing guarded owner. It adds no schema, ledger, signer, loader, network, or API factory. Errors expose stable codes rather than backend diagnostics or caller data. Existing generation/instance/close and abort handling apply; read aborts carry commit='none'.

This is a private prerequisite, not public getBalance or WalletBalance acceptance: scan/revision projection, public SDK integration, scheduling, signer integration, and loader qualification remain outstanding. Native bucket tests additionally cover distinct fields in every pool, uneconomic value, maximum amounts, and observed-total overflow.

The existing native fixture now includes an entirely empty account with an available scanned summary; encrypted uneconomic Sapling/Orchard/Ironwood notes (1/5000/5000 zatoshis); an immature 70000-zatoshi transparent coinbase output associated through the native API with a transaction scanned at index zero; and change detected by scanning a second block that spends a prior Sapling note. Exact change buckets in all three shielded pools are checked under one- and two-confirmation policies. These use scanner/native insertion APIs, not SQL-written accounting state. The fixture retains all original purpose, policy, and advisory-lock cases and exports eight databases with fifteen expected queries for generated tests.

The original Node fixture loop consumes every exported case. The original Firefox test now seeds those same native SQLite bytes through its dedicated worker's exclusive OPFS lease, then checks exact bigint bucket values/types, invalid policy, purpose differences, preabort without reads or mutations, database byte preservation, and close/destruction/reopen through the existing observed lifecycle. Mutation instrumentation counts writes, truncates, and deletes. All earlier VIEW, HD, mnemonic, and lifecycle assertions remain. This browser extension can also consume the four original immutable balance-build-01 databases.

Native coverage is distinct from generated-runtime acceptance: immutable balance-build-01's prior Node results qualify only its original source/fixtures. The continuation's new tests require a coordinator-assigned final-source output and generated Node/ordinary Firefox execution; the coverage worker does not build a new output or run browsers/listeners. Coinbase maturity transition is not asserted by this fixture.
